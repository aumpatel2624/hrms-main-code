# Shift & Attendance — Module Spec

## Purpose

This module tracks when employees actually work (via `Employee Checkin` device/app punches), defines the shifts they are scheduled to work (`Shift Type`, `Shift Assignment`, `Shift Request`, `Shift Schedule`, `Shift Schedule Assignment`, `Shift Location`, `Shift Assignment Tool`), and reconciles the two into a daily attendance record (`Attendance`, `Attendance Request`, `Employee Attendance Tool`) — either automatically (an hourly background pipeline that reads unconsumed checkins and marks Present/Absent/Half Day per shift-specific working-hour thresholds) or manually (HR staff bulk-marking attendance, or an employee/manager filing a correction request).

## Doctype List

| Doctype | Purpose |
|---|---|
| [[Shift Type]] | Defines a shift's time window, grace periods/margins, and all auto-attendance configuration (thresholds, holiday behavior, sync watermarks); hosts the core auto-attendance algorithm. |
| [[Shift Assignment]] | Assigns one employee to one Shift Type for a date range; submittable; hosts the shared shift-window time-resolution engine used across the module. |
| [[Shift Request]] | Employee-initiated, approver-gated request for a (usually temporary) shift change; on approval, generates a `Shift Assignment`. |
| [[Shift Schedule]] | A reusable named recurrence pattern (frequency + days-of-week) tied to one Shift Type, used to auto-generate a rolling series of `Shift Assignment` records. |
| [[Shift Schedule Assignment]] | Binds one employee to one `Shift Schedule`; the scheduled job walks these to auto-create upcoming `Shift Assignment` records on a rolling 90-day horizon. |
| [[Shift Assignment Tool]] | Single-doctype bulk UI/RPC tool: mass-assign shifts, mass-assign shift schedules, or mass-approve/reject Shift Requests. |
| [[Shift Location]] | A geofenced physical location (lat/long + radius) attachable to a Shift Assignment, enforced at checkin time. |
| [[Employee Checkin]] | One IN/OUT punch record (device, mobile, or manual); resolves and caches which shift occurrence it belongs to; feeds the auto-attendance pipeline; links back to the `Attendance` it produced. |
| [[Attendance]] | The daily per-employee record of Present/Absent/On Leave/Half Day/Work From Home status; submittable; created either by the auto-attendance pipeline, an Attendance Request, the Employee Attendance Tool, or manually. |
| [[Attendance Request]] | Submittable correction request (Work From Home / On Duty, optionally half-day) that creates or updates Attendance records for a date range on submit. |
| [[Employee Attendance Tool]] | Virtual single-doctype bulk UI/RPC tool for HR to mass-mark attendance (and resolve pending Half Day "other half" statuses) for a filtered set of employees on one date. |

## Recommended Target Schema Shape

Relational (Postgres/MySQL-style) table design:

- **`shift_types`** (from `Shift Type`) — one row per shift definition. Columns: `id` (PK, user-chosen string in source; recommend surrogate PK + unique `code`), `start_time`, `end_time`, `holiday_list_id` (FK -> `holiday_lists`, nullable), `determine_check_in_and_check_out` (enum), `working_hours_calculation_based_on` (enum), `working_hours_threshold_for_half_day` (numeric), `working_hours_threshold_for_absent` (numeric), `begin_check_in_before_shift_start_minutes` (int), `allow_check_out_after_shift_end_minutes` (int), `enable_auto_attendance` (bool), `process_attendance_after` (date, nullable), `last_sync_of_checkin` (timestamp, nullable), `auto_update_last_sync` (bool), `mark_auto_attendance_on_holidays` (bool), `enable_late_entry_marking`/`late_entry_grace_period`, `enable_early_exit_marking`/`early_exit_grace_period`, `allow_overtime` (bool), `overtime_type_id` (FK, nullable), `color` (enum/string).

- **`shift_assignments`** (from `Shift Assignment`) — one row per employee-shift-period. Columns: `id` PK, `employee_id` FK, `company_id` FK, `shift_type_id` FK, `shift_location_id` FK nullable, `status` (Active/Inactive), `overtime_type_id` FK nullable, `start_date`, `end_date` nullable, `shift_request_id` FK nullable, `shift_schedule_assignment_id` FK nullable, `docstatus`/submission metadata (`is_submitted`, `is_cancelled`, `amended_from_id` self-FK). Index on `(employee_id, status, start_date, end_date)` for the frequent "find employee's active shift on date" query pattern.

- **`shift_requests`** (from `Shift Request`) — `id` PK, `employee_id`, `shift_type_id`, `company_id`, `approver_user_id`, `from_date`, `to_date` nullable, `status` (Draft/Approved/Rejected), submission metadata, `amended_from_id` self-FK.

- **`shift_schedules`** (from `Shift Schedule`) — `id` PK (user-chosen code in source), `shift_type_id` FK, `frequency` (enum), submission metadata, `amended_from_id` self-FK.
  - **`shift_schedule_repeat_days`** (from `repeat_on_days` child table, doctype "Assignment Rule Day") — owned child rows: `id` PK, `shift_schedule_id` FK, `day` (enum Mon-Sun). Not a join table (the days are intrinsic to one schedule, not shared/many-to-many across schedules).

- **`shift_schedule_assignments`** (from `Shift Schedule Assignment`) — `id` PK, `employee_id` FK, `company_id` FK, `shift_schedule_id` FK, `shift_location_id` FK nullable, `shift_status` (Active/Inactive — value stamped onto generated Shift Assignments), `enabled` (bool), `create_shifts_after` (date — self-advancing watermark). Not submittable in source.

- **`shift_locations`** (from `Shift Location`) — `id` PK (recommend surrogate; source uses `location_name` as natural key with a uniqueness constraint), `location_name` (unique), `checkin_radius_meters` (int, nullable/0 = disabled), `latitude`, `longitude`.

- **`employee_checkins`** (from `Employee Checkin`) — `id` PK, `employee_id` FK, `log_type` (IN/OUT/blank), `shift_type_id` FK nullable, `time` (timestamp, effectively immutable once linked), `device_id` (string), `skip_auto_attendance` (bool), `attendance_id` FK nullable -> `attendances` (**this is the exact link-back field**), `shift_start`/`shift_end`/`shift_actual_start`/`shift_actual_end` (timestamps, cached resolved-shift-window snapshot), `offshift` (bool), `overtime_type_id` FK nullable, `latitude`/`longitude` (nullable), `geolocation` (geojson/jsonb). Index on `(shift_type_id, attendance_id, skip_auto_attendance, offshift, shift_actual_end)` to support the auto-attendance fetch query, and `(employee_id, time, log_type)` for duplicate-log detection.

- **`attendances`** (from `Attendance`) — `id` PK, naming-series-derived display code, `employee_id` FK, `working_hours` (numeric(precision 2)), `status` (enum: Present/Absent/On Leave/Half Day/Work From Home), `leave_type_id` FK nullable, `leave_application_id` FK nullable, `attendance_date`, `company_id` FK, `department_id` FK nullable, `shift_type_id` FK nullable, `attendance_request_id` FK nullable, `late_entry`/`early_exit` (bool), `half_day_status` (enum Present/Absent, nullable), `modify_half_day_status` (bool — internal "pending resolution" marker), `overtime_type_id` FK nullable, `standard_working_hours`/`actual_overtime_duration` (numeric), submission metadata, `amended_from_id` self-FK. Unique-ish constraint modeling: NOT a hard unique index on `(employee_id, attendance_date)` — source's duplicate check is conditional (see `Attendance.md` validation #4, involving `half_day_status`/`modify_half_day_status`/`shift`), so enforce this as an application-layer check, not a DB unique constraint, or a carefully-crafted partial unique index if the target DB supports it.

- **`attendance_requests`** (from `Attendance Request`) — `id` PK, `employee_id`, `department_id`, `company_id`, `from_date`, `to_date`, `half_day` (bool), `half_day_date` nullable, `include_holidays` (bool), `shift_type_id` FK nullable, `reason` (enum: Work From Home/On Duty), `explanation` (text), submission metadata, `amended_from_id` self-FK. **Port Note carried from `Attendance Request.md`**: source's `on_discard` references a `status` field that does not exist in this doctype's schema — decide during port design whether to add one or reproduce the anomaly.

- **`Employee Attendance Tool`** and **`Shift Assignment Tool`**: both are single-row/virtual/RPC-only doctypes in source with no real persisted entity — do not create tables for these; port them as stateless application service endpoints (see their respective `.md` files for full request/response contracts).

## Module-Wide Invariants

- **An employee can have at most one *Active*, submitted `Shift Assignment` whose date range overlaps another Active submitted assignment with an *overlapping shift timing* at a time** — enforced in `Shift Assignment.validate_overlapping_shifts`, but this constraint is **conditionally relaxable** by the site-wide `HR Settings.allow_multiple_shift_assignments` toggle (which downgrades same-date-different-shift conflicts to a warning, though same-*timing* overlap remains a hard error regardless of that toggle — see `Shift Assignment.md` validation rule #3). A port must implement this as a cross-record, timing-aware, toggle-sensitive invariant, not a simple "one active assignment per employee" uniqueness constraint.
- **At most one non-cancelled `Attendance` record should exist per (employee, attendance_date, shift)** combination, with the specific nuance that a shift-less Attendance and a shift-tagged Attendance for the same employee+date DO conflict with each other (see `Attendance.md` validation #4) — this is enforced procedurally in `validate()`, not by a DB constraint, and a port should replicate the exact OR-logic rather than a plain composite unique key.
- **Employee Checkin rows are the single source of truth feeding auto-attendance, and are consumed exactly once**: once a checkin's `attendance` link is set, its `time` field becomes immutable and it is excluded from all future auto-attendance fetch queries (`attendance is not set` filter). Cancelling the resulting Attendance record must unlink (`attendance = null`) every checkin that pointed to it, making them eligible for re-processing — this two-way consistency (link on create, unlink on cancel) is a module-wide invariant, not just an `Attendance.on_cancel` implementation detail.
- **The hourly auto-attendance/auto-shift-creation pipeline is strictly ordered**: `update_last_sync_of_checkin` -> `process_auto_attendance_for_all_shifts` -> `process_auto_shift_creation`, all under the `hourly_long` scheduler bucket (see `Shift Type.md` and `Shift Schedule Assignment.md`). This ordering is load-bearing (the second job reads the watermark the first job advances); a port's job scheduler must preserve it, whether as one composite job or three dependency-ordered jobs.
- **`Shift Type`, `Shift Assignment`, and `Employee Checkin` share one canonical shift-window resolution algorithm** (`get_shift_details`/`get_shift_timings`/`get_shift_for_time`/`get_actual_start_end_datetime_of_shift`, fully specified in `Shift Assignment.md`) that correctly handles overnight ("midnight") shifts and adjacent-shift margin overlaps. Every doctype in this module that needs "what shift covers this timestamp" must call the same shared implementation in the port — reimplementing a simplified version per call site is the single highest-risk source of behavioral drift identified while documenting this module.
- **Absence auto-marking always looks "one shift-cycle behind"** the configured `last_sync_of_checkin` watermark for each Shift Type, to leave a grace window for manual corrections before an Absent is auto-stamped (see `Shift Type.md` sections E-G) — this lag is intrinsic to the algorithm (derived from the previous shift occurrence's start date), not a separately configurable delay value.
